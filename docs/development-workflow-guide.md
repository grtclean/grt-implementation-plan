# GRT系统开发流程规范指南

本文档定义了GRT智能系统的标准化开发流程，确保Manus与Claude Code之间的高效协作，以及功能开发的质量保证。

---

## 1. 开发流程概述

GRT系统采用**Manus规划-Claude Code实施-Manus检查**的三阶段协作模式。每个功能从需求分析到交付验收，都遵循统一的流程规范。

| 阶段 | 负责方 | 主要职责 | 输出物 |
|------|--------|----------|--------|
| 规划阶段 | Manus | 需求分析、任务拆解、优先级排序 | 功能规格说明、任务清单 |
| 实施阶段 | Claude Code | 代码开发、单元测试、文档更新 | 代码变更、测试用例 |
| 检查阶段 | Manus | 功能验证、Bug修复、质量评估 | 验证报告、检查点 |

## 2. 任务管理规范

### 2.1 todo.md 文件规范

项目根目录的`todo.md`文件是任务管理的核心，所有功能开发必须在此文件中记录。

**格式要求：**
- 使用Markdown复选框格式：`- [ ]`表示待完成，`- [x]`表示已完成
- 主任务使用粗体标题，子任务缩进两个空格
- 任务完成后立即标记，不得延迟

**示例：**
```markdown
- [x] **任务1-年度规划前端页面**
    - [x] 创建年度规划管理页面（AnnualPlanning.tsx）
    - [x] 支持可视化编辑年度规划项目
    - [x] 支持版本切换和激活
```

### 2.2 任务优先级

| 优先级 | 标识 | 说明 |
|--------|------|------|
| P0 | 🔴 | 阻塞性问题，必须立即处理 |
| P1 | 🟠 | 核心功能，当前迭代必须完成 |
| P2 | 🟡 | 重要功能，尽量在当前迭代完成 |
| P3 | 🟢 | 增强功能，可延后处理 |

## 3. 代码开发规范

### 3.1 文件组织结构

```
grt-implementation-plan/
├── client/src/
│   ├── pages/           # 页面组件（每个功能一个文件）
│   ├── components/      # 可复用组件
│   ├── contexts/        # React Context
│   ├── hooks/           # 自定义Hooks
│   └── lib/             # 工具函数和配置
├── server/
│   ├── routers.ts       # tRPC路由定义
│   ├── db.ts            # 数据库操作函数
│   ├── webhook/         # Webhook集成模块
│   └── cron/            # 定时任务脚本
├── drizzle/
│   └── schema.ts        # 数据库Schema定义
├── docs/                # 项目文档
└── shared/              # 前后端共享代码
```

### 3.2 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 页面组件 | PascalCase | `AnnualPlanning.tsx` |
| 数据库表 | snake_case | `annual_planning_configs` |
| API路由 | camelCase | `annualPlanning.getConfigs` |
| 数据库函数 | camelCase | `getAnnualPlanningConfigs` |
| 测试文件 | kebab-case | `annual-planning.test.ts` |

### 3.3 代码注释要求

每个主要函数必须包含JSDoc注释，说明功能、参数和返回值：

```typescript
/**
 * 获取指定年度的规划配置列表
 * @param year - 年度（如2026）
 * @returns 规划配置数组
 */
export async function getAnnualPlanningConfigs(year: number) {
  // 实现代码
}
```

## 4. 单元测试规范

### 4.1 测试文件命名

测试文件放置在`server/`目录下，命名格式为`{feature}.test.ts`。

### 4.2 测试覆盖要求

| 功能类型 | 最低测试数量 | 必须覆盖场景 |
|----------|--------------|--------------|
| 数据库CRUD | 4个 | 创建、读取、更新、删除 |
| API端点 | 3个 | 正常请求、参数验证、错误处理 |
| 业务逻辑 | 5个 | 核心流程、边界条件、异常处理 |

### 4.3 测试模板

```typescript
import { describe, it, expect, vi } from "vitest";

describe("功能名称", () => {
  describe("子功能", () => {
    it("应该正确处理正常情况", () => {
      // 测试代码
    });

    it("应该正确处理边界条件", () => {
      // 测试代码
    });

    it("应该正确处理错误情况", () => {
      // 测试代码
    });
  });
});
```

## 6. 版本发布流程

### 6.1 版本号规范

采用语义化版本号：`主版本.次版本.修订号`

| 版本类型 | 说明 | 示例 |
|----------|------|------|
| 主版本 | 重大架构变更 | 1.0.0 → 2.0.0 |
| 次版本 | 新功能添加 | 1.3.0 → 1.4.0 |
| 修订号 | Bug修复和小改进 | 1.3.5 → 1.3.6 |

### 6.2 发布检查点

每次发布前必须完成：

1. **运行全部测试**：`pnpm test`
2. **检查项目状态**：`webdev_check_status`
3. **更新CHANGELOG.md**：记录所有变更
4. **保存检查点**：`webdev_save_checkpoint`

## 8. Manus-Claude协作流程

### 8.1 任务分配流程

```
Manus接收用户需求
    ↓
Manus更新todo.md添加任务
    ↓
Manus创建任务规划（plan tool）
    ↓
Claude Code实施开发
    ↓
Claude Code编写测试
    ↓
Manus验证功能
    ↓
Manus保存检查点
    ↓
Manus交付用户
```

### 8.2 问题反馈流程

当发现Bug或问题时：

1. Manus记录问题到todo.md
2. Manus分析问题原因
3. Claude Code修复代码
4. Manus验证修复结果
5. Manus更新验证报告

### 8.3 多界面协调开发

当功能涉及多个页面时：

1. **设计阶段**：先设计所有相关页面的交互流程
2. **API阶段**：统一设计后端API接口
3. **实施阶段**：按依赖顺序开发各页面
4. **集成阶段**：验证页面间的数据流转

## 9. 质量保证标准

### 9.1 代码质量

- TypeScript严格模式
- 无any类型（除非必要）
- 函数单一职责
- 代码复用优先

### 9.2 性能标准

- 页面首次加载 < 3秒
- API响应时间 < 500ms
- 无内存泄漏

### 9.3 用户体验

- 所有操作有加载状态
- 错误信息清晰友好
- 支持中英文切换
- 响应式布局
