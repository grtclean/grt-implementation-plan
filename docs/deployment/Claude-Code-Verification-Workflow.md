## 1. 概述

Claude Code代码查验流程是GRT智能系统开发中的核心质量保证机制。该流程建立了一套结构化的开发-验证循环，确保每个功能在交付前经过严格的AI辅助审查和自动化测试验证。

### 1.1 流程目标

本流程旨在实现以下目标：

**质量保证**: 通过多层次的代码审查和测试，确保代码质量符合企业级标准。

**一致性维护**: 确保代码风格、架构模式和命名规范在整个项目中保持一致。

**知识传承**: 通过文档化的查验过程，积累开发经验和最佳实践。

**风险控制**: 及早发现和解决潜在问题，降低生产环境故障风险。

### 1.2 适用范围

本流程适用于GRT智能系统的所有代码变更，包括：

| 变更类型 | 适用性 | 查验级别 |
|----------|--------|----------|
| 新功能开发 | 必须 | 完整查验 |
| Bug修复 | 必须 | 标准查验 |
| 代码重构 | 必须 | 完整查验 |
| 配置变更 | 推荐 | 简化查验 |
| 文档更新 | 可选 | 基础审查 |

Manus作为规划和检查组件，承担以下职责：

## 3. 开发查验循环

### 3.1 循环概述

开发查验循环是一个迭代过程，每个功能必须经过完整的循环才能被视为完成。循环包含以下阶段：

**阶段1 - 需求确认**: 确保对需求的理解准确无误。

**阶段2 - 设计评审**: 评估技术方案的可行性和合理性。

**阶段3 - 代码实现**: 按照设计规范编写代码。

**阶段4 - 质量检查**: 验证代码是否符合要求。

**阶段5 - 修复迭代**: 修复发现的问题并重新验证。

**阶段6 - 最终确认**: 确认所有检查项通过后完成任务。

### 3.2 阶段1：需求确认

在开始任何开发工作之前，必须完成需求确认：

```markdown
## 需求确认清单

### 功能需求
- [ ] 功能目标是否明确
- [ ] 用户场景是否清晰
- [ ] 输入输出是否定义
- [ ] 边界条件是否说明

### 技术需求
- [ ] 是否需要数据库变更
- [ ] 是否需要新增API
- [ ] 是否影响现有功能
- [ ] 是否需要新增依赖

### 非功能需求
- [ ] 性能要求是否明确
- [ ] 安全要求是否说明
- [ ] 兼容性要求是否定义
- [ ] 可维护性要求是否考虑
```

### 3.3 阶段2：设计评审

设计评审确保技术方案的合理性：

```markdown
## 设计评审清单

### 架构设计
- [ ] 是否符合现有架构模式
- [ ] 模块划分是否合理
- [ ] 接口设计是否清晰
- [ ] 数据流是否明确

### 数据库设计
- [ ] 表结构是否合理
- [ ] 索引设计是否优化
- [ ] 关联关系是否正确
- [ ] 数据迁移是否考虑

### API设计
- [ ] 路由命名是否规范
- [ ] 参数定义是否完整
- [ ] 返回格式是否统一
- [ ] 错误处理是否完善
```

### 3.4 阶段3：代码实现

代码实现阶段的规范：

**文件组织**

```
功能模块/
├── server/
│   ├── services/
│   │   └── feature.service.ts      # 业务逻辑
│   └── featureRoutes.ts            # tRPC路由
├── client/
│   └── src/
│       ├── components/
│       │   └── FeatureComponent.tsx # UI组件
│       └── pages/
│           └── FeaturePage.tsx      # 页面组件
└── tests/
    └── feature.test.ts              # 测试文件
```

**代码规范**

```typescript
// 服务层示例
import { getDb } from '../db';
import { z } from 'zod';

// 输入验证Schema
const createFeatureInput = z.object({
  name: z.string().min(1).max(100),
  description: z.string().optional(),
  status: z.enum(['active', 'inactive']).default('active'),
});

type CreateFeatureInput = z.infer<typeof createFeatureInput>;

/**
 * 创建功能
 * @param data 创建参数
 * @returns 创建结果
 */
export async function createFeature(data: CreateFeatureInput) {
  // 验证输入
  const validated = createFeatureInput.parse(data);
  
  // 获取数据库连接
  const db = await getDb();
  if (!db) {
    throw new Error('Database connection not available');
  }
  
  // 执行业务逻辑
  const result = await db.insert(features).values(validated);
  
  return {
    success: true,
    id: result.insertId,
  };
}
```

### 3.5 阶段4：质量检查

质量检查包含以下步骤：

**TypeScript类型检查**

```powershell
# 运行类型检查
pnpm check

# 检查特定文件
npx tsc --noEmit server/services/feature.service.ts
```

**单元测试**

```powershell
# 运行所有测试
pnpm test

# 运行特定测试
pnpm test -- --grep "feature"

# 运行测试并生成覆盖率报告
pnpm test -- --coverage
```

**代码风格检查**

```powershell
# 运行格式化
pnpm format

# 检查格式化状态
pnpm format --check
```

## 5. Bug修复流程

### 5.1 Bug分类

| 级别 | 定义 | 响应时间 | 处理优先级 |
|------|------|----------|------------|
| P0-致命 | 系统崩溃/数据丢失 | 立即 | 最高 |
| P1-严重 | 核心功能不可用 | 4小时内 | 高 |
| P2-一般 | 功能异常但有替代方案 | 24小时内 | 中 |
| P3-轻微 | 体验问题/UI瑕疵 | 下个版本 | 低 |

**修复尝试超限**: 经过3次修复尝试仍未解决。

**资源不足**: 需要额外资源或专业知识。

## 7. 版本控制规范

### 7.1 提交信息规范

提交信息遵循Conventional Commits规范：

```
<type>(<scope>): <subject>

<body>

<footer>
```

**类型(type)**

| 类型 | 说明 |
|------|------|
| feat | 新功能 |
| fix | Bug修复 |
| docs | 文档更新 |
| style | 代码格式调整 |
| refactor | 代码重构 |
| perf | 性能优化 |
| test | 测试相关 |
| chore | 构建/工具变更 |

**示例**

```
feat(lead): 添加商机智能推荐功能

- 实现基于历史数据的推荐算法
- 添加推荐结果展示组件
- 集成到商机管理页面

Reviewed-by: Claude Code
Tested-by: Vitest (32 tests passed)
Closes: #123
```

### 7.2 分支策略

```
main (生产分支)
  │
  ├── develop (开发分支)
  │     │
  │     ├── feature/xxx (功能分支)
  │     │
  │     └── bugfix/xxx (修复分支)
  │
  └── hotfix/xxx (紧急修复分支)
```

### 7.3 检查点保存

每个重要变更完成后，使用Manus保存检查点：

```powershell
# 通过Manus保存检查点
# 检查点描述应包含:
# - 版本号

# "v1.3.20: 修复TypeScript类型警告，添加核心页面功能引导，优化移动端响应式布局"
```

## 9. 最佳实践

### 9.1 开发最佳实践

**代码组织**

将相关代码放在一起，遵循"功能内聚"原则。每个功能模块应包含服务层、路由层和测试文件。

**错误处理**

使用统一的错误处理模式，确保所有错误都被捕获并返回友好的错误信息。

```typescript
// 统一错误处理示例
export async function safeExecute<T>(
  operation: () => Promise<T>,
  errorMessage: string
): Promise<T> {
  try {
    return await operation();
  } catch (error) {
    console.error(`${errorMessage}:`, error);
    throw new Error(errorMessage);
  }
}
```

**日志记录**

在关键操作处添加日志记录，便于问题排查。

```typescript
// 日志记录示例
console.log(`[${new Date().toISOString()}] Creating feature:`, {
  name: data.name,
  userId: ctx.user.id,
});
```

### 9.2 查验最佳实践

**增量查验**

不要等到所有代码完成后才进行查验，而是在每个小功能完成后立即进行查验。

**自动化优先**

优先使用自动化工具进行查验，减少人工审查的工作量。

**文档同步**

代码变更时同步更新相关文档，避免文档与代码不一致。

### 9.3 协作最佳实践

**清晰沟通**

在Manus和Claude Code之间保持清晰的沟通，确保需求和反馈准确传达。

**及时反馈**

发现问题后及时反馈，避免问题积累。

**知识共享**

将解决问题的经验记录下来，形成知识库供后续参考。
