## 1. 概述

本文档定义了GRT智能系统在本地Windows 11服务器开发部署过程中，使用Claude Code进行代码查验的标准流程。该流程采用**Manus-Claude协作模式**，确保代码质量、系统稳定性和开发效率。

### 1.1 流程目标

代码查验流程旨在实现以下目标：

| 目标 | 说明 |
|------|------|
| 代码质量保证 | 确保代码符合TypeScript类型安全、编码规范和最佳实践 |
| 功能完整性 | 验证实现的功能完全满足需求规格 |
| 系统稳定性 | 通过测试确保新代码不破坏现有功能 |
| 安全合规 | 检查潜在的安全漏洞和数据泄露风险 |
| 可维护性 | 确保代码结构清晰、注释完整、易于维护 |

### 1.2 适用场景

代码查验流程适用于以下场景：

- 新功能开发完成后的代码审查
- Bug修复后的验证
- 重构或优化后的回归测试
- 部署前的最终检查
- 版本发布前的质量门禁

### 3.2 阶段详解

**阶段1：前置检查**

前置检查确保开发环境处于正确状态，避免因环境问题导致的假阳性错误。

```powershell
# 执行前置检查
pnpm install --frozen-lockfile  # 确保依赖完整
# 检查.env文件存在且包含必要变量
# 测试数据库连接
```

**阶段2：Claude Code 实现**

Claude Code根据Manus的任务指令进行代码实现。实现过程中应遵循以下原则：

1. **理解需求**：确保完全理解任务要求后再开始编码
2. **增量实现**：分步骤实现，每步完成后进行自检
3. **类型安全**：充分利用TypeScript类型系统
4. **错误处理**：考虑边界条件和异常情况
5. **代码注释**：为复杂逻辑添加清晰注释

**阶段3：自动化检查**

自动化检查通过脚本执行，确保客观、一致的检查结果。

```powershell
# 运行自动化检查脚本
.\scripts\code-review.ps1
```

**阶段4：Manus 验收**

Manus对Claude Code的实现进行验收，检查以下方面：

| 检查项 | 验收标准 |
|--------|----------|
| 功能完整性 | 所有需求点都已实现 |
| 代码质量 | 无明显的代码异味 |
| 测试覆盖 | 关键路径有测试覆盖 |
| 文档完整 | 必要的注释和文档已添加 |

1. 打开VS Code扩展市场

3. 安装官方Claude Code扩展
4. 配置API密钥

**配置settings.json**

```json

  "claude.apiKey": "${env:ANTHROPIC_API_KEY}",
  "claude.model": "claude-3-opus-20240229",
  "claude.maxTokens": 4096,
  "claude.temperature": 0.3

**全面代码审查**

```

### 5.3 批量审查脚本

创建批量审查脚本 `scripts/batch-review.ps1`：

```powershell
# 批量代码审查脚本
param(
    [string]$Directory = "server/services",
    [string]$Pattern = "*.ts"
)

$files = Get-ChildItem -Path $Directory -Filter $Pattern -Recurse

foreach ($file in $files) {
    Write-Host "审查文件: $($file.FullName)" -ForegroundColor Yellow
    
    # 这里可以集成Claude API调用
    # 或者生成审查任务清单
    
    $reviewTask = @{
        File = $file.FullName
        Status = "待审查"
        Timestamp = Get-Date
    }
    
    # 输出到审查日志
    $reviewTask | ConvertTo-Json | Add-Content "logs/review-queue.json"
}

Write-Host "已添加 $($files.Count) 个文件到审查队列" -ForegroundColor Green
```

## 7. 三次尝试规则

### 7.1 规则说明

根据结构化开发流程要求，每个问题最多尝试修复3次。如果3次尝试后仍未解决，需要执行升级处理流程。

### 7.2 尝试流程

**第一次尝试**

1. Claude Code分析问题原因
2. 实现修复方案
3. 执行自动化检查
4. Manus验收

**第二次尝试（如第一次失败）**

1. 分析第一次失败原因
2. 调整修复方案
3. 重新实现
4. 执行检查和验收

**第三次尝试（如第二次失败）**

1. 深入分析问题根因
2. 考虑替代方案
3. 实现并验证
4. 如仍失败，执行升级处理

### 7.3 升级处理流程

当3次尝试后问题仍未解决，执行以下步骤：

**步骤1：保存调试信息**

```powershell
# 创建调试日志目录
$debugDir = "docs/debug-logs/$(Get-Date -Format 'yyyyMMdd_HHmmss')"
New-Item -ItemType Directory -Path $debugDir -Force

# 保存相关信息
Copy-Item "logs/*.log" $debugDir
# 保存问题描述和尝试记录
```

**步骤2：评估影响**

| 评估项 | 内容 |
|--------|------|
| 功能影响 | 哪些功能受影响 |
| 用户影响 | 影响多少用户 |
| 业务影响 | 对业务的影响程度 |
| 临时方案 | 是否有临时绕过方案 |

**步骤3：记录遗留问题**

在 `docs/issues/backlog.md` 中记录：

```markdown
## 遗留问题 - [问题ID]

### 问题概述
[简要描述]

### 尝试记录
[3次尝试的详细记录]

### 影响评估
[影响评估结果]

### 建议处理时机
- [ ] 下个版本
- [ ] 重大重构时
- [ ] 技术债务清理时

### 临时方案
[如有临时方案，描述方案]
```

**步骤4：继续后续任务**

记录完成后，继续执行后续任务，不阻塞整体进度。

## 8. 最佳实践

### 8.1 代码实现最佳实践

| 实践 | 说明 |
|------|------|
| 小步提交 | 每完成一个小功能就提交，便于回滚 |
| 先写测试 | 采用TDD方式，先写测试再实现 |
| 类型优先 | 先定义类型接口，再实现逻辑 |
| 错误处理 | 每个可能失败的操作都要有错误处理 |
| 日志记录 | 关键操作添加日志，便于调试 |

### 8.2 代码审查最佳实践

| 实践 | 说明 |
|------|------|
| 及时审查 | 代码完成后立即审查，避免积压 |
| 聚焦重点 | 优先关注业务逻辑和安全问题 |
| 建设性反馈 | 提供具体的改进建议，而非简单否定 |
| 知识分享 | 审查过程中分享最佳实践 |
| 持续改进 | 根据审查发现优化编码规范 |

### 8.3 问题修复最佳实践

| 实践 | 说明 |
|------|------|
| 理解根因 | 先理解问题根本原因，再修复 |
