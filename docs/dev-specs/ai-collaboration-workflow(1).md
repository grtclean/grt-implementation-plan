## 1. 概述

本文档定义了 GRT 智能系统在 Windows 11 本地服务器环境下的多 AI 协作开发工作流。该工作流整合了 Manus（任务规划）、Claude Code（功能实现）和 ChatGPT（迭代优化）三个 AI 工具，形成结构化的开发验证循环。

### 1.1 AI 角色分工

| AI 工具 | 角色 | 主要职责 | 触发时机 |
|---------|------|----------|----------|
| **Manus** | 规划者 | 需求分析、任务分解、进度管理、验收测试 | 项目启动、需求变更、阶段验收 |
| **Claude Code** | 实现者 | 代码编写、功能开发、单元测试、Bug修复 | 收到任务规格后 |
| **ChatGPT** | 优化者 | 代码审查、性能优化、文档生成、方案评审 | 代码提交前、性能问题发现时 |
| **Gemini** | 顾问 | 技术决策支持、知识库查询、问题诊断 | 技术选型、疑难问题 |

### 1.2 工作流核心原则

1. **强制前置检查**: 执行后续任务前，必须检查最近添加的功能是否存在Bug
2. **完整需求审查**: 确认所有先前的流程和开发需求已完全满足
3. **结构化验证循环**: 实现→检查→修复→再检查，直到通过
4. **未解决Bug管理**: 最多3次尝试后，记录问题并继续

### 2.2 阶段详细说明

#### 阶段1: 需求分析（Manus）

**输入**: 用户需求描述

**输出**: 任务规格文档

**执行步骤**:

1. 分析需求，识别功能边界
2. 分解为可执行的子任务
3. 定义验收标准
4. 生成任务规格文档

**任务规格模板**:

```markdown
## 任务规格: [功能名称]

### 1. 功能描述
[详细描述功能目标和用户价值]

### 2. 技术要求
- 数据库变更: [是/否，具体说明]
- API接口: [需要创建的tRPC过程]
- 前端页面: [需要创建/修改的组件]

### 3. 验收标准
- [ ] 标准1
- [ ] 标准2
- [ ] 单元测试覆盖率 > 80%

### 4. 依赖关系
- 前置任务: [列表]
- 相关模块: [列表]

### 5. 预估工时
- 开发: X小时
- 测试: X小时
```

#### 阶段2: 功能实现（Claude Code）

**输入**: 任务规格文档

**输出**: 功能代码 + 单元测试

**执行步骤**:

1. 阅读任务规格，确认理解
2. 设计数据模型（如需要）
3. 实现后端API
4. 实现前端UI
5. 编写单元测试
6. 本地验证

**代码提交清单**:

```markdown
## 代码提交清单

### 变更文件
- [ ] drizzle/schema.ts (如有数据库变更)
- [ ] server/db.ts (数据库查询助手)
- [ ] server/routers.ts (tRPC过程)
- [ ] client/src/pages/Xxx.tsx (前端页面)
- [ ] server/services/xxx.test.ts (单元测试)

### 自检项目
- [ ] TypeScript编译无错误
- [ ] 单元测试全部通过
- [ ] 代码格式化完成
- [ ] 无硬编码敏感信息
```

#### 阶段3: 代码审查（ChatGPT）

**输入**: Claude Code 提交的代码

**输出**: 审查报告 + 优化建议

**审查维度**:

| 维度 | 检查项 | 严重程度 |
|------|--------|----------|
| 类型安全 | TypeScript类型完整性 | 高 |
| 错误处理 | 异常捕获和处理 | 高 |
| 安全性 | SQL注入、XSS防护 | 高 |
| 性能 | N+1查询、内存泄漏 | 中 |
| 可维护性 | 代码结构、命名规范 | 中 |
| 最佳实践 | React/Node.js规范 | 低 |

**审查报告模板**:

```markdown
## 代码审查报告

### 审查概要
- 审查文件数: X
- 发现问题数: X (高:X, 中:X, 低:X)
- 整体评分: X/10

### 问题列表

#### 高优先级
1. [问题描述]
   - 位置: xxx.ts:行号
   - 建议: [修复建议]

#### 中优先级
...

### 优化建议
1. [优化建议1]
2. [优化建议2]

### 结论
- [ ] 通过，可合并
- [ ] 需修改后重新审查
```

#### 阶段4: 验收测试（Manus）

**输入**: 代码 + 审查报告

**输出**: 验收结果

**验收步骤**:

1. 运行完整测试套件
2. 检查验收标准是否满足
3. 验证功能是否符合需求
4. 确认无回归问题

## 3. Bug修复工作流

### 3.1 Bug处理流程

```
发现Bug → Manus分析 → Claude Code修复 → ChatGPT审查 → Manus验证
    ↑                                                      │
    └──────────────── 未通过（最多3次）────────────────────┘
                            │
                      超过3次
                            ↓
                    记录并继续后续任务
```

### 3.2 未解决Bug管理

当Bug在3次尝试后仍未解决时：

1. **记录问题**: 在 `docs/dev-logs/unresolved-bugs.md` 中记录
2. **影响评估**: 评估对系统的影响程度
3. **临时方案**: 如可能，提供临时绕过方案
4. **后续计划**: 建议何时重新处理

**未解决Bug记录模板**:

```markdown
## Bug #[编号]: [标题]

### 基本信息
- 发现日期: YYYY-MM-DD
- 严重程度: 高/中/低
- 影响范围: [描述]

### 问题描述
[详细描述]

### 尝试的修复方案
1. 方案1: [描述] - 结果: [失败原因]
2. 方案2: [描述] - 结果: [失败原因]
3. 方案3: [描述] - 结果: [失败原因]

### 影响评估
- 功能影响: [描述]
- 用户影响: [描述]
- 数据影响: [描述]

### 临时方案
[如有]

### 建议重新处理时机
[条件或时间]
```

## 6. 最佳实践

### 6.1 沟通规范

1. **任务交接**: 使用标准化的任务规格文档
2. **问题反馈**: 包含完整的上下文和复现步骤
3. **代码审查**: 提供具体的行号和修改建议

### 6.2 质量保证

1. **测试优先**: 先写测试，再写实现
2. **小步提交**: 每个提交只做一件事
3. **持续集成**: 每次提交都运行完整测试

### 6.3 文档维护

1. **同步更新**: 代码变更时同步更新文档
2. **版本记录**: 在CHANGELOG中记录所有变更
3. **知识沉淀**: 将解决方案记录到知识库
