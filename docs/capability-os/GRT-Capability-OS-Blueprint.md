## 1. 系统定位与核心理念

### 1.1 从功能系统到能力操作系统

GRT 智能系统不再是 HRM、项目管理、服务管理等功能模块的简单组合，而是一个以**能力（Capability）为核心**的操作系统。这一转变的本质是：**从管理"事务"转向管理"能力"，从记录"结果"转向驱动"成长"**。

| 维度 | 传统功能系统 | 能力操作系统（Capability OS） |
|------|-------------|------------------------------|
| **核心主数据** | 项目、客户、订单 | 能力（Capability） |
| **系统目标** | 流程管理、数据记录 | 能力培养、能力验证、能力复用 |
| **人员定位** | 执行者、资源 | 能力载体、能力贡献者 |
| **项目定位** | 交付目标 | 能力训练场、能力验证场 |
| **客户定位** | 服务对象 | 能力需求方、能力验证方 |
| **问题定位** | 需要解决的异常 | 能力提升的机会 |

### 1.2 为什么这样设计

**解决的核心问题**：

1. **能力不可见**：传统系统只记录"谁做了什么"，但不知道"谁具备什么能力"。当需要派遣工程师时，只能依赖主管的主观判断。

2. **能力不可计算**：工程师的能力等级依赖人工评估，主观性强、周期长、标准不一。

3. **能力不可复制**：优秀工程师的经验停留在个人脑中，离职即流失，新人成长缓慢。

4. **交付质量不可控**：Tier1 客户对交付质量要求极高，但缺乏系统性保障机制。

**设计原则**：

> **能力是组织的核心资产，项目是能力的训练场，客户是能力的验证方，问题是能力提升的催化剂。**

## 2. 能力作为一级主数据

### 2.1 能力数据模型

在 Capability OS 中，**能力（Capability）** 是与客户、项目、人员同等重要的一级主数据。所有业务活动都围绕能力展开。

| 数据层级 | 传统系统 | Capability OS |
|----------|----------|---------------|
| **一级主数据** | 客户、项目、产品 | **能力**、客户、项目、人员 |
| **二级数据** | 订单、任务、工时 | 能力证据、能力评估、能力应用 |
| **三级数据** | 日志、记录 | 问题、改进、知识 |

### 2.2 能力分类体系

| 能力域 | 能力类别 | 典型能力项 |
|--------|----------|------------|
| **现场服务能力** | 设备调试 | 超声波清洗机调试、真空干燥系统调试 |

| | 质量检测 | 外观检测、功能测试、性能验证 |
| | 工艺优化 | 工艺参数优化、节拍优化 |
| **项目交付能力** | 项目管理 | 进度管理、风险管理、资源协调 |

2. **能力可追溯**：每个能力都有明确的获取路径、验证记录、应用场景。

3. **能力可匹配**：当项目需要特定能力时，系统可以自动匹配具备该能力的人员。

## 3. 能力等级体系 L1-L5

### 3.1 等级定义

能力等级采用 **L1-L5** 五级体系，每个等级都有**可计算、可验证**的标准，不依赖人工主观评估。

| 等级 | 名称 | 定义 | 核心特征 |
|------|------|------|----------|
| **L1** | 学习者 Learner | 正在学习该能力，尚未独立执行 | 需要全程指导 |
| **L2** | 执行者 Executor | 可在指导下独立完成标准任务 | 需要检查确认 |
| **L3** | 熟练者 Proficient | 可独立完成复杂任务，能处理常见异常 | 可独立交付 |
| **L4** | 专家 Expert | 可指导他人，能处理疑难问题 | 可带教新人 |
| **L5** | 大师 Master | 可定义标准，推动能力体系演进 | 可创新方法 |

### 3.2 能力证据（Evidence）驱动机制

能力等级的升降完全由**能力证据（Evidence）**驱动，系统自动计算，无需人工评估。

| 证据类型 | 说明 | 权重 | 示例 |
|----------|------|------|------|
| **任务完成** | 独立完成相关任务 | 30% | 完成10次超声波清洗机调试 |
| **问题解决** | 解决相关技术问题 | 25% | 解决3次控制系统故障 |
| **知识贡献** | 输出知识文档或培训 | 20% | 编写调试手册、培训新人 |
| **客户认可** | 获得客户正面反馈 | 15% | Tier1客户验收通过 |
| **同行认可** | 获得专家或同事认可 | 10% | 专家评审通过 |

### 3.3 能力等级计算模型

```
能力等级 = f(证据积分, 证据质量, 证据时效)

其中：
- 证据积分 = Σ(证据权重 × 证据数量)
- 证据质量 = 加权平均(任务复杂度, 问题难度, 客户等级)
- 证据时效 = 时间衰减函数(最近证据权重更高)
```

| 等级 | 积分要求 | 质量要求 | 时效要求 |
|------|----------|----------|----------|
| L1→L2 | ≥100分 | 标准任务 | 6个月内有效证据 |
| L2→L3 | ≥300分 | 复杂任务 | 12个月内有效证据 |
| L3→L4 | ≥600分 | 疑难问题 + 带教记录 | 18个月内有效证据 |
| L4→L5 | ≥1000分 | 创新方法 + 标准制定 | 24个月内有效证据 |

### 3.4 能力升级路径

```
┌─────┐    任务完成×10     ┌─────┐    复杂任务×20    ┌─────┐
│ L1  │ ─────────────────► │ L2  │ ────────────────► │ L3  │
│学习者│    + 培训通过      │执行者│    + 问题解决×5   │熟练者│
└─────┘                    └─────┘                   └─────┘
                                                        │
                                                        │ 疑难问题×10
                                                        │ + 带教×3
                                                        ▼
┌─────┐    创新方法×3      ┌─────┐
│ L5  │ ◄───────────────── │ L4  │
│大师 │    + 标准制定       │专家 │
└─────┘                    └─────┘
```

### 3.5 为什么这样设计

**解决的问题**：

1. **消除主观评估**：传统的能力评估依赖主管打分，标准不一、周期长。L1-L5体系完全由系统计算，客观公正。

2. **激励持续成长**：工程师可以清晰看到自己的能力等级和升级路径，形成持续成长的动力。

3. **支撑精准派遣**：当项目需要L3级超声波调试能力时，系统可以自动筛选符合条件的工程师。

4. **保障交付质量**：Tier1项目可以设置能力门槛，确保只有具备足够能力的工程师才能参与。

## 4. Tier1 红蓝对抗交付体系

### 4.1 Tier1 客户的战略地位

Tier1 客户（如大型汽车制造商、半导体企业）对交付质量的要求远高于普通客户。一次交付失败可能导致：

- 客户生产线停机，损失巨大
- 客户信任丧失，影响长期合作
- 行业口碑受损，影响市场拓展

因此，**Tier1 交付必须内嵌系统级约束**，不能依赖个人能力和责任心。

### 4.2 红蓝对抗机制

**红蓝对抗**是 Tier1 和高复杂度项目的**强制流程**，不可跳过。

| 角色 | 职责 | 目标 |
|------|------|------|
| **红队（交付团队）** | 执行交付任务 | 按时、按质完成交付 |
| **蓝队（挑战团队）** | 审查、挑战、验证 | 发现潜在问题，确保交付质量 |

### 4.3 红蓝对抗流程

```
┌────────────────────────────────────────────────────────────────┐
│                    Tier1 红蓝对抗交付流程                        │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐    │
│  │ 方案设计 │───►│ 蓝队审查 │───►│ 执行交付 │───►│ 蓝队验证 │    │
│  │  红队    │    │  挑战   │    │  红队    │    │  确认   │    │
│  └─────────┘    └────┬────┘    └─────────┘    └────┬────┘    │
│                      │                              │          │
│                      ▼                              ▼          │
│               ┌─────────────┐              ┌─────────────┐    │
│               │ 问题清单    │              │ 验证报告    │    │
│               │ 必须闭环    │              │ 客户签收    │    │
│               └─────────────┘              └─────────────┘    │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### 4.4 蓝队审查检查清单

| 审查维度 | 检查项 | 通过标准 |
|----------|--------|----------|
| **能力匹配** | 交付人员能力等级是否满足要求 | 核心岗位≥L3 |
| **方案完整** | 技术方案是否覆盖所有风险点 | 风险清单100%覆盖 |
| **资源充足** | 工具、备件、文档是否齐全 | 资源清单100%确认 |
| **应急预案** | 异常情况处理方案是否明确 | 预案演练通过 |
| **历史教训** | 是否规避了历史问题 | 知识库检索确认 |

### 4.5 强制约束条件

| 约束类型 | 约束内容 | 违反后果 |
|----------|----------|----------|
| **能力门槛** | 核心岗位必须≥L3，关键岗位必须≥L4 | 系统阻止派遣 |
| **蓝队审查** | 方案必须通过蓝队审查 | 无法进入执行阶段 |
| **问题闭环** | 蓝队发现的问题必须闭环 | 无法进入下一阶段 |
| **验证签收** | 必须获得蓝队验证和客户签收 | 项目无法结项 |

### 4.6 为什么这样设计

**解决的问题**：

1. **消除侥幸心理**：红蓝对抗是强制流程，不能因为"时间紧"或"人手不够"而跳过。

2. **前置风险发现**：蓝队在交付前发现问题，比客户在现场发现问题，成本低100倍。

3. **建立质量文化**：通过制度保障，让"高质量交付"成为组织习惯，而非个人自觉。

4. **保护客户关系**：Tier1客户的信任是战略资产，一次失败可能需要数年才能修复。

## 5. 系统性学习机制

### 5.1 核心原则：问题只允许发生一次

> **同一个问题，在组织内只允许发生一次。第二次发生，是系统的失败，不是个人的失败。**

这一原则的实现需要完整的**问题→根因→措施→固化**闭环。

### 5.3 根因分析方法

|----------|----------|--------|

| **培训课程** | 将典型问题纳入培训内容 | "常见故障诊断"培训增加该案例 |
| **系统约束** | 将强制要求嵌入系统流程 | 系统强制要求FAT前完成阻抗测试 |

### 5.6 为什么这样设计

**解决的问题**：

1. **打破"重复犯错"的魔咒**：很多组织的问题是"同样的坑，不同的人反复踩"。系统性学习机制确保每个问题都转化为组织能力。

2. **降低对个人经验的依赖**：当经验沉淀在系统中，新人可以快速获取，老员工离职不会带走知识。

3. **持续提升交付质量**：每解决一个问题，组织的能力就提升一点，交付质量持续改善。

### 7.2 角色分工

| 角色 | 定位 | 职责 | 边界 |
|------|------|------|------|
| **NocoBase** | 核心业务平台 | 数据管理、流程执行、用户交互 | 所有业务数据的唯一真实来源 |
| **Manus** | 规划与表达层 | 系统规划、蓝图维护、文档生成、对外沟通 | 不直接操作业务数据 |
| **AI（Gemini等）** | 建议与分析引擎 | 数据分析、建议生成、预测 | **仅提供建议，不具备决策权** |

### 7.3 AI的角色边界

> **核心原则：AI是顾问，不是决策者。**

| AI可以做 | AI不可以做 |
|----------|------------|
| 分析数据，发现趋势 | 自动修改业务数据 |
| 提供建议和方案 | 自动执行业务决策 |
| 预测风险和机会 | 自动派遣人员 |
| 生成报告和文档 | 自动审批流程 |
| 辅助诊断问题 | 自动关闭问题 |

### 7.4 为什么这样设计

**解决的问题**：

1. **明确职责边界**：避免系统间职责重叠和冲突，每个系统专注于自己的核心价值。

2. **保障数据一致性**：NocoBase作为唯一数据源，避免多系统数据不一致。

3. **控制AI风险**：AI的建议需要人工确认后才能执行，避免AI错误导致业务损失。

4. **支撑持续演进**：清晰的分层架构便于各层独立升级和优化。
