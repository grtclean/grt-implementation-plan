## 2. 部署与版本更新规范

```
├─────────────────────────────────────────────────────────────┤
│                      应用服务层 (Node.js + Express)          │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │  Web Server │  │  API Server │  │  WS Server  │         │
│  └─────────────┘  └─────────────┘  └─────────────┘         │
├─────────────────────────────────────────────────────────────┤
│                      AI引擎层 (Gemini + Claude)              │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │ 判断引擎    │  │ 执行引擎    │  │ 诊断引擎    │         │
│  │ (Gemini)    │  │ (Claude)    │  │ (Gemini)    │         │
│  └─────────────┘  └─────────────┘  └─────────────┘         │
├─────────────────────────────────────────────────────────────┤
│                      数据存储层                              │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │  MySQL/TiDB │  │  Redis      │  │  S3 Storage │         │
│  └─────────────┘  └─────────────┘  └─────────────┘         │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 初始部署流程

#### 2.2.1 环境准备阶段

在开始部署之前，需要确保目标服务器满足以下硬件和软件要求。硬件配置应根据预期用户规模和数据量进行选择，最低配置适用于开发测试环境，推荐配置适用于中小规模生产环境，高可用配置适用于大规模企业部署。

| 配置项 | 最低配置 | 推荐配置 | 高可用配置 |
|-------|---------|---------|-----------|
| CPU | 2核 | 4核 | 8核×3节点 |
| 内存 | 4GB | 8GB | 16GB×3节点 |
| 磁盘 | 20GB SSD | 50GB SSD | 100GB SSD×3节点 |
| 网络 | 10Mbps | 100Mbps | 1Gbps内网 |

软件环境要求如下表所示，所有版本号均为最低要求版本：

| 软件 | 版本要求 | 安装命令 |
|------|---------|---------|
| Node.js | 22.x | `curl -fsSL https://deb.nodesource.com/setup_22.x \| sudo -E bash - && sudo apt install -y nodejs` |
| pnpm | 9.x | `npm install -g pnpm` |
| MySQL | 8.0+ | `sudo apt install mysql-server` |
| Docker | 24.0+ | `curl -fsSL https://get.docker.com \| sh` |
| Nginx | 1.24+ | `sudo apt install nginx` |

#### 2.2.2 Docker部署步骤

Docker部署是推荐的部署方式，可以确保环境一致性并简化运维工作。以下是完整的Docker部署步骤：

**步骤1：获取部署包**

```bash
# 克隆代码仓库
git clone https://github.com/grt-system/grt-implementation-plan.git
cd grt-implementation-plan

# 或从发布页面下载
wget https://releases.grt-system.com/v4.5.0/grt-system-v4.5.0.tar.gz
tar -xzf grt-system-v4.5.0.tar.gz
```

**步骤2：配置环境变量**

```bash
# 复制环境变量模板
cp docker/config.env.template docker/config.env

# 编辑配置文件
nano docker/config.env
```

必须配置的环境变量包括：

| 变量名 | 必需 | 说明 | 示例值 |
|-------|-----|------|-------|
| DATABASE_URL | ✅ | MySQL连接字符串 | `mysql://user:pass@host:3306/grt` |
| JWT_SECRET | ✅ | JWT签名密钥(32位以上) | `your-secure-jwt-secret-key-here` |
| GEMINI_API_KEY | ⚠️ | Gemini AI API密钥 | `AIza...` |
| JIANDAOYUN_API_KEY | ⚠️ | 简道云API密钥 | `jdy_...` |
| JIANDAOYUN_CORP_ID | ⚠️ | 简道云企业ID | `68e...` |
| S3_ACCESS_KEY | ⚠️ | S3存储访问密钥 | `AKIA...` |
| S3_SECRET_KEY | ⚠️ | S3存储密钥 | `wJal...` |

**步骤3：启动服务**

```bash
# 构建并启动所有服务
docker-compose up -d

# 查看服务状态
docker-compose ps

# 查看日志
docker-compose logs -f
```

**步骤4：初始化数据库**

```bash
# 进入应用容器
docker-compose exec app sh

# 运行数据库迁移
pnpm db:push

# 退出容器
exit
```

**步骤5：验证部署**

```bash
# 健康检查
curl http://localhost:3000/api/health

# 预期响应
# {"status":"healthy","version":"4.5.0","timestamp":"2026-01-24T..."}
```

#### 2.2.3 源码部署步骤

对于需要自定义配置或无法使用Docker的环境，可以采用源码部署方式：

**步骤1：安装依赖**

```bash
cd grt-implementation-plan
pnpm install
```

**步骤2：配置数据库**

```bash
# 创建数据库
mysql -u root -p << EOF
CREATE DATABASE grt_system CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'grt_user'@'localhost' IDENTIFIED BY 'your_password';
GRANT ALL PRIVILEGES ON grt_system.* TO 'grt_user'@'localhost';
FLUSH PRIVILEGES;
EOF

# 配置环境变量
cp .env.example .env
nano .env
```

**步骤3：运行迁移**

```bash
pnpm db:push
```

**步骤4：构建生产版本**

```bash
pnpm build
```

**步骤5：启动服务**

```bash
# 使用PM2管理进程
pm2 start ecosystem.config.js

# 或直接启动
NODE_ENV=production node dist/index.js
```

### 2.3 版本更新流程

版本更新是系统运维的重要环节，需要遵循严格的流程以确保更新过程的安全性和可回滚性。

#### 2.3.1 更新前准备

在执行任何更新操作之前，必须完成以下准备工作：

| 检查项 | 操作 | 验证方法 |
|-------|------|---------|
| 备份数据库 | `mysqldump -u root -p grt_system > backup_$(date +%Y%m%d).sql` | 检查备份文件大小 |
| 备份配置文件 | `cp .env .env.backup` | 对比文件内容 |
| 记录当前版本 | `cat package.json \| grep version` | 记录到更新日志 |
| 通知相关人员 | 发送更新通知邮件 | 确认收到回复 |
| 选择更新窗口 | 选择低峰时段 | 检查系统负载 |

#### 2.3.2 Docker环境更新

```bash
# 1. 拉取最新镜像
docker-compose pull

# 2. 停止当前服务
docker-compose down

# 3. 备份数据卷
docker run --rm -v grt_data:/data -v $(pwd):/backup alpine tar czf /backup/data_backup.tar.gz /data

# 4. 启动新版本
docker-compose up -d

# 5. 运行数据库迁移
docker-compose exec app pnpm db:push

# 6. 验证更新
curl http://localhost:3000/api/health
```

#### 2.3.3 源码环境更新

```bash
# 1. 拉取最新代码
git fetch origin
git checkout v4.5.0

# 2. 安装新依赖
pnpm install

# 3. 运行数据库迁移
pnpm db:push

# 4. 重新构建
pnpm build

# 5. 重启服务
pm2 restart all

# 6. 验证更新
curl http://localhost:3000/api/health
```

#### 2.3.4 回滚流程

如果更新后发现问题，需要立即执行回滚操作：

```bash
# Docker环境回滚
docker-compose down
docker-compose -f docker-compose.backup.yml up -d

# 源码环境回滚
git checkout v4.4.0
pnpm install
pnpm build
pm2 restart all

# 数据库回滚（如有必要）
mysql -u root -p grt_system < backup_20260124.sql
```

### 2.4 部署后检查确认

部署完成后，必须执行以下检查确认流程：

| 检查类别 | 检查项 | 预期结果 | 检查命令 |
|---------|-------|---------|---------|
| 服务状态 | 应用进程 | 运行中 | `pm2 status` |
| 服务状态 | 数据库连接 | 正常 | `curl /api/trpc/system.dbHealth` |
| 功能验证 | 用户登录 | 成功 | 手动测试 |
| 功能验证 | API响应 | 正常 | `curl /api/trpc/system.health` |
| 性能检查 | 响应时间 | <500ms | `curl -w "%{time_total}" /api/health` |
| 安全检查 | HTTPS证书 | 有效 | `openssl s_client -connect host:443` |

### 3.2 产品命名规范

产品命名遵循统一的编码规则，确保产品识别的唯一性和可追溯性：

```
产品编码格式: [系列代码]-[容量代码]-[功能代码]-[版本号]

示例: USC-500L-4F-V2
      │    │    │   └── 版本号：第2代
      │    │    └────── 功能代码：4频超声
      │    └─────────── 容量代码：500升
      └──────────────── 系列代码：超声波清洗
```

| 编码段 | 含义 | 取值范围 |
|-------|------|---------|
| 系列代码 | 产品系列 | USC/SPR/VAC/HYB/AUT |
| 容量代码 | 槽体容量 | 50L-5000L |
| 功能代码 | 功能特性 | 1F-8F(频率)/HT(加热)/VD(真空) |
| 版本号 | 产品版本 | V1-V9 |

### 3.4 Methodology方法论

GRT智慧系统的核心方法论基于以下原则：

**AI-AI销售系统方法论（RFC-036）**

该方法论定义了五大智能体的协作模式，形成从客户需求到方案交付的闭环：

| 智能体 | 职责 | 输入 | 输出 |
|-------|------|------|------|
| Listener | 需求采集 | 客户对话/文档 | 结构化需求 |
| Estimator | 方案估算 | 结构化需求 | 初步方案 |
| Negotiator | 商务谈判 | 初步方案 | 商务条款 |
| Guardian | 合规审查 | 商务条款 | 合规报告 |
| Builder | 方案构建 | 合规方案 | 最终交付物 |

**四层透明度模型**

信息透明度按照访问权限分为四个层级，确保敏感信息的安全性：

| 层级 | 可见性 | 内容类型 | 访问控制 |
|------|-------|---------|---------|
| L0 | 公开 | 能力介绍、案例摘要 | 无需登录 |
| L1 | 注册用户 | 技术白皮书 | 需注册 |
| L2 | 授权客户 | 项目状态、报价 | 需授权 |
| L3 | 内部 | 工艺参数、成本 | 仅内部 |

## 6. 实时BI与项目状态

### 6.1 M0-M12项目阶段定义

GRT智慧系统采用M0-M12门径管理模型，每个阶段都有明确的交付物和门禁条件：

| 阶段 | 名称 | 关键交付物 | 门禁条件 | 责任人 |
|------|------|-----------|---------|-------|
| M0 | 商机识别 | 客户需求初评 | 需求可行性确认 | 销售 |
| M1 | 需求确认 | 技术规格书(GTR/CSR) | 技术方案可行 | 销售+设计 |
| M2 | 方案设计 | 初步方案 | 方案评审通过 | 设计 |

## 10. 德美跨国合规与员工管理

本章节详细阐述GRT智慧系统在德国和美国双重法律管辖下的考勤管理、合规性监控及数据隐私保护解决方案。该设计基于NocoBase无代码/低代码开发平台，支持Claude Code编程实施和Gemini判断优化。

### 10.1 监管环境与合规性分析

#### 10.1.1 德国合规要求

德国联邦劳动法院（BAG）在2022年9月13日的裁决（1 ABR 22/21）彻底改变了“信任工作制”的现状。法院依据《职业健康与安全法》（ArbSchG）第3条第2款第1项，裁定雇主有法律义务引入一个系统，用于全面记录员工每日工作时间的开始、结束和持续时间。

| 要求项 | 具体规定 | 系统实现 |
|-------|---------|----------|
| 记录精度 | 必须记录确切的开始/结束时间 | 统一采用datetime字段记录精确时间点 |
| 休息时间 | 6h+必须休息30min，9h+需休息45min | 配置区域性规则引擎，DE用户触发强制扣除逻辑 |
| 差旅时间 | “第一客户”原则（计入工作时间） | 引入Travel Context字段，结合Home Base判定 |
| 数据隐私 | 极高（GDPR），禁止非必要监控 | 实现字段级权限控制，对敏感字段加密 |
| 每日工时上限 | 每日上限10小时，需补休 | 实时计算逻辑，DE触发合规警报 |

#### 10.1.2 美国合规要求

根据美国《公平劳动标准法》（FLSA），雇主必须支付所有“遭受或允许”的工作时间的工资。对于远程员工，如果雇主“知道或有理由相信”员工正在工作，即使该工作未被明确要求，雇主也必须支付加班费。

| 要求项 | 具体规定 | 系统实现 |
|-------|---------|----------|
| 记录精度 | 记录总工时即可，但需精确到分钟 | 统一采用datetime字段 |
| 加班规则 | 周超40小时需支付1.5倍薪资 | 实时计算逻辑，US触发成本警报 |
| 外部销售豁免 | 主要职责必须是进行销售，惯常在营业场所之外工作 | 位置上下文追踪，生成豁免资格风险预警 |
| 推定知情 | 雇主必须支付所有知道或应知道的工作时间 | 非预定工作时间确认机制 |
